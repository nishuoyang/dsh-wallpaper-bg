# 两个已知限制的根因分析与解决方案

> 分支：`analysis/known-limitations`（只分析与方案，不改运行时代码）
> 适用版本：dsh-wallpaper-bg 0.5.17
> 目标：针对「内置壁纸首次加载约 5 秒空白」和「亮色壁纸下设置面板对比度偏低」给出根因、可选方案、利弊与推荐优先级；不触碰壁纸渲染、WE 代理、队列、上传等无关功能。
>
> **实施状态（2026-10-30）**：P0-a（400w 本地 WebP + 骨架/淡入 + 远程回退）、P0-b（设置弹窗作用域 0.86 + 文字档）、P1（10 张 1920w WebP 背景本地化，q70，约 2.09 MB）与 P2（按弹窗区域亮度自适应 alpha 0.82–0.90，遮罩折损，无亮度图回退 .86）均已实现。

## 0. 结论摘要

| 优先级 | 问题 | 推荐动作 | 预计改动 | 风险 |
| --- | --- | --- | --- | --- |
| P0 | 内置壁纸首次加载空白 | 10 张 **400w 缩略图本地化（WebP）** + 骨架占位 + 图片淡入 | 新增约 150–300 KB 资源；`BUILTIN_ITEMS`、`tile()`、几行 CSS | 低 |
| P0 | 设置面板对比度 | 只对「含 `.wbg-panel` 的设置弹窗」把 `bg-layer-2` 提到 0.86，并把 tertiary / caption 文字色各调深/调亮一档 | 作用域 CSS + 少量 token；不全局改 alpha | 低 |
| P1 | 内置壁纸背景仍要联网 | 10 张 1920w **AVIF/WebP 本地化**（或至少默认第一张），保留远程作回退 | 新增约 0.8–1.5 MB；`image-set()` / `srcset` | 中（包体、编码流程） |
| P2 | 任意壁纸的自适应对比度 | 复用现有亮度图，按面板下方壁纸亮度动态选 alpha / 文字档 | 需要采样与缓存；逻辑更复杂 | 中 |
| P2 | 首次之后仍走网络 | Service Worker 缓存 / preconnect / `fetchpriority` | 仅在前两档不采用时才有意义 | 低–中 |

**推荐落地顺序：P0 缩略图本地化 + 骨架 → P0 设置弹窗作用域对比度 → P1 背景本地化 → P2 自适应。** 前两项可以各自独立发一个小版本，互不阻塞；P1 取决于包体预算，P2 只在实测仍有个别壁纸不达标时再做。

## 1. 限制一：内置壁纸依赖 Unsplash，首次加载约 5 秒空白

### 1.1 现象

- 首次打开「设置 → 壁纸 → 内置壁纸」时，网格里只有半透明白底和标题，图片位置是空的；网络慢时 3–6 秒才逐张出现。
- 选中某张内置壁纸后，背景也要等 1920w 主图下载 + 解码完成才交叉淡入；首次安装没有上一张壁纸，等待期间看到的是 `#dsh-wallpaper-bg` 的近黑底色或页面自身背景。
- 断网时内置壁纸完全不可用（自定义上传不受影响）。

### 1.2 根因链路（代码位置）

1. **内置壁纸只有 Unsplash photo id，没有本地资源。** `lib/client.js` 顶部的 `BUILTIN` 只保存 10 个 `photo-...` 字符串；`BUILTIN_ITEMS` 在运行时用 `unsplashUrl(photo, 1920, 80)` / `unsplashUrl(photo, 400, 60)` 拼出远程 URL。首次渲染没有任何本地像素可画。
2. **网格一次并发 10 个远程缩略图，且没有骨架 / 占位。** `tile()` 直接渲染 `<img src=... loading="lazy">`；`.wbg-tile` 只有 `background: var(--dsw-alias-bg-layer-2)`（半透明白），图片未到达时就是一块空白卡片。`loading="lazy"` 还会让靠近视口的过程受浏览器调度影响。
3. **主图要等下载 + 解码才入场。** `applyImage()` 先 `loadImage()`（`new Image()` → `onload` → `img.decode()`），成功后才创建 `.wbg-layer` 并交叉淡入；首次没有旧图层，等待期间没有画面。`loadImage` 是正确做法（避免换图空窗），但缺少「先给一张低清图 / 主色」的过渡。
4. **串行瓶颈由最慢的那张决定。** 10 张并行请求里只要有一张慢（实测一张 400w 图 TTFB 2.43s / 总 3.21s），用户就会觉得「整个网格还没加载完」，因为空白卡片之间没有区分「加载中」和「加载失败」。

### 1.3 实测数据

2026-10-28 在本机用 `curl` 对 10 个 400w/q60 缩略图做 10 并发测量（单次样本，仅用于判断量级）：

| 指标 | 结果 |
| --- | --- |
| 单张 TTFB | 0.216–2.432 s，9 张 < 0.31 s，1 张 2.43 s |
| 单张总耗时 | 0.225–3.208 s |
| 10 张并行总墙钟 | 3.69 s |
| 单张体积 | 14.5–34.9 KB，合计约 231 KB |
| 1920w/q80 首图 | 316.9 KB，总耗时 0.51 s（另一次 1280w 样本 1.48 s，波动大） |
| 960w/q80 首图 | 91.4 KB，总耗时 0.27 s |

之前 0.5.16 的全新安装审计里，无头 Edge 打开面板 1.8 s 时 10 张只到了 5 张，6 s 后才全部到齐；与这里「最慢一张 3.2 s + 解码 + 渲染」的量级一致。结论：**不是图片总量大（约 230 KB），而是「远程 + 无占位 + 最慢请求决定观感」**。

### 1.4 可选方案与利弊

| 方案 | 做法 | 效果 | 成本 / 风险 |
| --- | --- | --- | --- |
| **A. 本地化 400w 缩略图** | 把 10 张 400w 图压成 WebP（q70 左右）放进包内，`BUILTIN_ITEMS.thumbnail` 指向包内路径 | 网格首屏即出图；断网也能看到网格；仍可保留远程 1920w 主图 | +150–300 KB；需要构建/压缩流程；Unsplash 许可允许再分发，但建议在 README 补一句来源与许可 |
| **B. 本地化 1920w 主图** | 再把 10 张主图压成 AVIF/WebP（或 1280w 折中）放进包内 | 背景也即时、离线可用；彻底摆脱 Unsplash 运行时依赖 | +0.8–1.5 MB（AVIF 约 80–150 KB/张）；包体从 2.2 MB 到 3–3.7 MB；需要 `image-set()` 或运行时选格式 |
| **C. LQIP 内联占位** | 每张生成 20–32px 的 base64 缩略图（约 0.5–1 KB），作为 tile 背景；原图加载后淡入 | 几乎立刻有颜色/构图，空白感消失；包体只增加约 8–15 KB | 仍要联网才有清晰图；断网只有模糊占位；需要生成 LQIP 的脚本 |
| **D. 预连接 + 优先级** | `<link rel=preconnect>` 到 `images.unsplash.com`；首屏 4 张 `loading="eager" fetchpriority="high"`，其余 lazy | 可能把 3–6 s 降到 1–3 s，零资源 | 不解决断网/慢网；Unsplash 仍可能慢；优先级对 HTTP/2 多路复用收益有限 |
| **E. Service Worker 缓存** | 首次访问后缓存 10 张缩略图/主图，二次打开秒开 | 二次访问体验好 | 首次仍空白；SW 生命周期/版本清理复杂；与 DSH 的 origin 和插件更新耦合，不建议为 10 张图引入 |

补充：**只把 `loading="lazy"` 改成 eager 并不会解决首屏**——10 张仍要等网络，只是更早发起；**只加骨架**能改善「看起来坏了」的感受，但图像仍会一张张迟到。所以推荐「骨架 + 本地缩略图」组合，而不是单点优化。

### 1.5 推荐实现

**第一步（P0）：方案 A + 骨架 + 淡入。**

- 资源：`assets/builtin/thumb-01.webp` … `thumb-10.webp`，400w、q70–75，目标合计 ≤ 250 KB；同步在 `package.json.files` 增加 `assets/builtin/`（否则 npm 包不会带这些文件）。
- `BUILTIN` / `BUILTIN_ITEMS`：增加本地 `thumb` 字段（包内相对路径，客户端用 `new URL(..., import.meta.url)` 或 DSH 插件静态资源路径解析；需确认 `dsh.client` 注入的资源基址），`thumbnail` 仍保留远程 URL 作为回退。
- `tile()`：`img` 增加 `onLoad` 标记 `wbg-loaded`、`onError` 标记 `wbg-failed`；`loading` 首屏 4 张改 `eager`，其余保留 `lazy`，并加 `decoding="async"`。
- CSS：`.wbg-tile` 用 `--dsw-alias-bg-skeleton` 或中性渐变做骨架；`img{opacity:0;transition:opacity .18s}`，`.wbg-tile.wbg-loaded img{opacity:1}`；失败时显示首字占位（复用现有 `.wbg-tile-ph`）。
- 主图：`applyImage` 前先铺一张本地 400w 缩略图（`background-image`）或 CSS 主色，等 1920w 解码后交叉淡入；不改变现有交叉淡入和画质路径。

**第二步（P1）：方案 B（可选，按包体预算）。**

- 10 张 1920w AVIF/WebP（长边 1920，q60–70），目标 ≤ 1.2 MB；用 `image-set()` 提供 AVIF/WebP/JPEG 回退，或运行时按 `canvas.toDataURL('image/avif')` 能力选格式（更推荐 CSS `image-set`）。
- 如果预算紧张，只本地化 **默认第一张**（`FALLBACK_ITEM`）即可保证「首次安装第一眼有图」，其余仍远程；这是成本最低的离线兜底。

**不做**：不引入 Service Worker、不把 10 张图内联进 `client.js`（会让单文件 bundle 膨胀、解析变慢），不改 `loadImage` / 交叉淡入 / 色调补偿路径。

## 2. 限制二：亮色壁纸下设置面板对比度偏低

### 2.1 现象

- 浅色主题 + 深色壁纸、或深色主题 + 亮色壁纸时，设置弹窗里的次要文字（说明、计数、滑杆标签）发灰、发虚，左侧导航尤其明显。
- 亮色壁纸下弹窗整体像「蒙了一层白布」，深色壁纸下则像「蒙了一层灰」；文本对比度不稳定，随壁纸内容变化。
- 主页面正文、输入框通常还可读，问题集中在**大面积半透明弹窗 + 次要文字**。

### 2.2 根因链路（颜色取值来源）

1. **表面色被全局改成固定 alpha。** `applySurfaceMode()` 通过 `theme.overrideTokens()` 把 `--dsw-alias-bg-layer-2` 固定为浅色 `rgba(255,249,253,0.62)`、深色 `rgba(30,22,38,0.62)`；`bg-layer-1` 为 0.55，侧栏 0.5。设置弹窗的面板背景正是 `layer-2`。
2. **弹窗背景 = 表面色 × 0.62 + 壁纸 × 0.38。** 壁纸亮度直接参与合成：浅色主题遇到黑壁纸，面板从 255 掉到约 158；深色主题遇到白壁纸，面板从 30 升到约 116。文字色是按「接近不透明的浅/深表面」设计的，合成表面漂移到中灰后，对比度就崩了。
3. **文字色只做了色相偏移，没有按合成表面重新校对比度。** `AZURE_ROSE.light` 的 secondary `#4c5872`、tertiary `#6a7690`、caption `#78839b`，以及 dark 的 `#b6c1d9` / `#97a3bd` / `#8792ac`，在原始不透明表面上达标；但半透明合成后没有兜底。
4. **弹窗没有独立的可读底层。** 左侧导航、说明文字直接坐在 `layer-2` 上，没有局部 scrim / 毛玻璃 / 更实的卡片；DSH 的 `--dsw-alias-bg-mask-1` 也在半透明化后参与合成，进一步放大漂移。

### 2.3 对比度实测（WCAG 2.x，正文目标 4.5:1）

按当前 0.62 alpha 合成，取纯黑 / 深灰 / 中灰 / 亮灰 / 纯白五种壁纸亮度：

| 主题 | 壁纸 | 合成表面 RGB | secondary | tertiary | caption |
| --- | --- | --- | --- | --- | --- |
| 浅色 | 黑 | 158,154,157 | **2.57** | **1.64** | **1.37** |
| 浅色 | 中灰 | 207,203,206 | 4.44 | **2.84** | **2.37** |
| 浅色 | 白 | 255,251,254 | 6.95 | 4.45 | **3.71** |
| 深色 | 黑 | 19,14,24 | 10.53 | 7.51 | 6.10 |
| 深色 | 中灰 | 67,62,72 | 5.75 | 4.10 | **3.33** |
| 深色 | 白 | 116,111,120 | **2.71** | **1.93** | **1.57** |

结论：**不是「亮色壁纸」单方向的问题，而是「壁纸亮度与主题相反」时必然发生**；浅色主题遇暗壁纸、深色主题遇亮壁纸都会低于 AA。单靠调文字颜色无法同时覆盖两端，必须让表面更实或自适应。

### 2.4 可选方案与利弊

| 方案 | 做法 | 效果 | 成本 / 风险 |
| --- | --- | --- | --- |
| **A. 只给设置弹窗加实表面** | `[role="dialog"]:has(.wbg-panel)` 内把 `--dsw-alias-bg-layer-2` 提到 0.86（浅/深各自原色），并把 tertiary/caption 调深/调亮一档 | 最坏情况 secondary/tertiary/caption 均可 ≥ 4.6；只影响壁纸设置弹窗 | 弹窗比页面其他表面更实，视觉一致性略变；`:has()` 需 Chromium 105+ / Safari 15.4+ / Firefox 121+；不支持时回退为当前行为 |
| **B. 弹窗局部 scrim / 毛玻璃** | 在弹窗背后加一层半透明遮罩或 `backdrop-filter: blur(6–10px)` | 保留半透明观感，降低壁纸高频细节对文字的干扰 | `backdrop-filter` 在 4K 视频上可能增加合成开销；与 DSH 自带 mask 叠加可能变脏；需要实测 60fps |
| **C. 自适应表面** | 复用 `buildToneMap()` 的亮度图，计算弹窗区域平均亮度，动态选 alpha 或深/浅文字档 | 任意壁纸都能达标；观感最稳 | 逻辑复杂；弹窗打开/切壁纸时要重算；可能出现轻微跳变；需要缓存 |
| **D. 只调文字/边框** | 把 secondary/tertiary/caption 整体调深/调亮，加字重或轻微文字阴影 | 改动最小，不牺牲透明度 | 浅色遇黑壁纸时 tertiary/caption 仍难达标（当前色即使纯白表面也只有 4.0/3.36）；可能让文字显得过重 |
| **E. 全局提高 layer-2** | 直接把全局 `bg-layer-2` 从 0.62 提到 0.86 | 所有弹窗/菜单都更可读 | 影响所有使用 layer-2 的界面与第三方插件；侧栏/菜单会明显变实，违背「半透明壁纸」的整体设计；不推荐 |

补充：**不能改 `--dsw-alias-bg-mask-1` 来单独解决**——它会连带影响 `dsh-better-sidebar` 的上传/mermaid 遮罩，且之前已评估过暂不采用（见项目记忆）。

### 2.5 推荐实现

**P0：方案 A（作用域实表面 + 文字档），不做毛玻璃。**

作用域选择器（优先 `:has`，不支持时由插件在弹窗出现时加 `data-wbg-settings` 类）：

```css
/* 只命中包含壁纸面板的设置弹窗；不影响其他 dialog / 菜单 */
[role="dialog"]:has(.wbg-panel) {
  --dsw-alias-bg-layer-2: rgba(255, 249, 253, 0.86);  /* light */
  --dsw-alias-label-tertiary: #4f5b73;
  --dsw-alias-label-caption: #525d75;
}
body[data-ds-dark-theme] [role="dialog"]:has(.wbg-panel) {
  --dsw-alias-bg-layer-2: rgba(30, 22, 38, 0.86);
  --dsw-alias-label-tertiary: #a3aec7;
  --dsw-alias-label-caption: #b3bed6;
}
```

按 0.86 alpha + 上述文字色的最坏情况（浅色遇纯黑、深色遇纯白）：

| 主题 | secondary | tertiary | caption |
| --- | --- | --- | --- |
| 浅色 / 黑壁纸 | 4.97 | 4.76 | 4.62 |
| 深色 / 白壁纸 | 6.33 | 5.14 | 6.13 |

- 只覆盖弹窗内部的 `layer-2`，不改全局 token；主页面、侧栏、菜单、第三方插件表面保持现状。
- tertiary/caption 的调整也只在这个弹窗内生效；正文/主文字不动。
- `:has` 不支持时：在 `WallpaperPanel` 挂载时向上找最近的 `[role=dialog]` 加 `data-wbg-settings`，卸载时移除；CSS 同时写 `[data-wbg-settings]` 选择器。这是 10 行左右的兼容层，不影响其他功能。
- **作用域副作用**：`:has(.wbg-panel)` 只在壁纸页签激活、面板挂载时命中；从「通用设置 / 模型 / 插件」切到「壁纸」时，弹窗表面会从 0.62 变成 0.86，可能出现一次轻微跳变。若实测跳变明显，可在弹窗打开期间就给 dialog 加 `data-wbg-settings`（所有设置页统一 0.86），代价是通用 / 模型 / 插件页也变实；建议先做窄作用域，实测后再决定是否扩大。
- 如果实测 0.86 仍不够（例如用户自定义了极亮壁纸 + 深色主题 + 大面积图片），再进入 P2 自适应，而不是继续全局加 alpha。

**P2（可选）：方案 C 自适应**——复用 `buildToneMap` 已经算好的 32×32 亮度图，按弹窗矩形取平均亮度，映射到 0.82–0.90 的 alpha 或两档文字色；只在打开弹窗/切壁纸时算一次，避免每帧。收益是观感最稳，但复杂度明显高于 P0，不建议第一版就做。

## 3. 推荐优先级与验收

### 3.1 顺序

1. **P0-a：内置壁纸 400w 缩略图本地化 + 骨架/淡入。** 直接消灭「空白 5 秒」的第一印象；不动主图加载与画质；包体仅 +150–300 KB。
2. **P0-b：设置弹窗作用域对比度。** 只改一个弹窗的表面与两组文字 token；修复可读性/可访问性，不影响全局透明度。
3. **P1：内置壁纸 1920w 本地化（AVIF/WebP）。** 在包体预算允许时做；至少本地化默认第一张作为离线兜底。
4. **P2：自适应表面 / 毛玻璃。** 只在 P0-b 实测仍有个别壁纸不达标，或产品明确要求「任意壁纸都保持半透明」时再做；先测 4K 视频下的帧率。
5. **P2：Service Worker / preconnect。** 只有决定长期保留远程图片时才考虑；否则本地化后不再需要。

### 3.2 验收标准

- 内置壁纸：清空缓存后首次打开面板，**1 秒内 10 张卡片都有可辨认的缩略图**（本地资源应接近即时）；断网时网格仍可见；选中壁纸后背景在 1 秒内出现（本地主图）或先显示缩略图再淡入主图。
- 设置弹窗：浅色+纯黑壁纸、深色+纯白壁纸两种极端下，secondary / tertiary / caption 的对比度均 ≥ 4.5:1；弹窗内正文 ≥ 7:1；不改变弹窗外任何界面的 alpha。
- 性能：4K 视频壁纸播放时打开/关闭设置弹窗，帧率不低于改动前（不以 `backdrop-filter` 换对比度）。
- 兼容：`:has` 不可用时弹窗仍能获得 `data-wbg-settings` 类；不出现「设置弹窗打不开 / 面板错位」。
- 包体：npm tarball 增量有记录；P0 阶段不超过 +300 KB，P1 阶段不超过 +1.5 MB。

### 3.3 明确不做

- 不改 `loadImage` / `applyImage` 的交叉淡入与解码策略（已有防空窗逻辑）。
- 不改全局 `bg-layer-1/2`、侧栏 alpha、`bg-mask-1`（会波及其他界面与第三方插件）。
- 不加全屏 `filter` / 全屏 `backdrop-filter`（守住 4K 视频 60fps）。
- 不动 WE 代理、队列、自定义上传、色调补偿等无关功能。

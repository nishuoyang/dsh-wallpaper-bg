dsh-wallpaper-bg 性能评估

v0.5.12 · 一次性审计 · 数据全部来自本机实测（非估算）· 2026-10-13

本次评估把插件的两个半（lib/host.js 宿主端 + lib/client.js 浏览器端）分别挂到真实的 Node 服务和真实 Chromium 上跑基准，用本机 Wallpaper Engine 库的 314 张真实壁纸作为数据源。 结论是：插件整体性能相当健康——渲染层的合成策略（video + object-fit、恒等滤镜不挂 filter、双层叠化） 都是对的，实测没有帧率问题。真正值得改的是 5 个具体点，集中在「重复劳动」和「缺少并发合并」两类。

三个被数据推翻的直觉——这几处原本以为是瓶颈，实测证明不是，不建议改动：
  • 全屏 blur(20px) 不会掉帧：1080p 视频下 0/5/20 px 三档实测都是 161–165 fps。代码里「恒等滤镜不挂 filter」的规避仍然值得保留（4K 下未测，但至少 1080p 无代价）。
  • client.js 117 KB 不是负担：解析 + 编译 + factory 执行合计 1.5 ms，冷启动里完全可以忽略。
  • 视频预热不会把 GB 级文件整个拉下来：浏览器只缓冲「够播」的量就主动断开——实测 526 MB / 4 分钟的视频只缓冲 13.2 s（5%，约 28 MB），188 MB 的缓冲 8%，101 MB 的只缓冲 3%。

三、优化清单（按优先级）

本章是评估当时的原始清单，保留作对照用；每一项的处置结果见第五节。

P0 1. 内置壁纸冷启动要 1.7 秒才出背景

现象：每次 DSH 冷启动，首屏背景有约 1.7 秒停在容器底色 #0b0d12。

根因：BUILTIN_ITEMS 固定请求 w=1920 全尺寸图（client.js:53-61）， 且插件不落任何本地缓存，每次启动都从 unsplash CDN 拉 309 KB。

建议（两条独立，可分别做）：

  • 按屏幕分辨率请求：用 Math.min(1920, Math.ceil(screen.width * devicePixelRatio / 100) * 100) 选宽度。1080p 屏从 1920 降到 1280 能省约 40% 流量，4K 屏则反过来不再被放大发虚。
  • 渐进式出图：先用 640px 缩略图（几十 KB、约 150 ms）挂上背景，再用全尺寸图静默替换。用户侧感知从 1.7 s 降到 0.2 s 以内，且完全不引入「缓存文件」，不违背 README 的 zero-cache 承诺。

预期：首屏背景出现时间 1.70 s → 0.2 s 以内。

P0 2. 自定义上传的视频缩略图，单个 2 秒且每次刷新全部重算

现象：打开「自定义上传」页签，每传一个视频要约 2 秒才出缩略图；刷新页面后所有视频缩略图重新生成。

根因：generateVideoThumb()（client.js:1341-1378）每次都要 URL.createObjectURL(blob) 把整个视频读进来 → loadeddata → canvas 取帧 → toBlob。 结果只存进内存 Map（vidThumbCache），不落 IndexedDB，所以刷新即失效。

建议：在 IndexedDB 里加一个 thumbs object store（keyPath:'id'）， 把生成好的缩略图 blob 连同源 blob 的 size 一起存；读取时若命中且 size 一致就直接用。 上传的图片缩略图同理可省。

预期：首次仍 2 s/个（ unavoidable ），但二次进入 0 ms；上传 10 个视频的场景从 20 s 降到 2 s。

P0 3. 拖滑杆单帧 10 ms，且随壁纸库线性变差

现象：拖动「背景模糊度 / 亮度 / 安全放大」滑杆时，每帧约 10 ms；WE 页签下这一帧里包含重建 314 个 tile。

根因：setState() 无条件 saveState() + emit()（client.js:942-965）， 而 emit() 让 WallpaperPanel 整体重渲染——weGrid() 会把整个网格的 element 树重建一遍。 实测 localStorage 只占 0.068 ms，瓶颈 100% 是全量重渲染。

建议（最小改动优先）：

  • 滑杆行抽成独立组件，只通过 useState 持有自己的值，onChange 里直接改 DOM 样式（setFilter/setZoom 已经是现成的），onMouseUp/onBlur 时才 setState 提交。
  • weGrid() / customGrid() 加记忆化：用 useMemo 依赖 [weList, weTypeFilter, weRatingFilter, snap.wallpaperId, snap.syncDesktop]，外观类字段不进入依赖。
  • 若库规模继续增长（>800 张），再考虑虚拟滚动——现在 314 张 ≈ 1256 个元素，还不到必须虚拟化的程度。

预期：拖滑杆单帧 10 ms → 接近 0 ms；且不再随壁纸库规模线性劣化。

P1 4. /we 没有 in-flight 合并，并发请求成倍穿透

现象：慢下游（500 ms）下并发 10 个请求，WE API 被真实请求了 10 次，10 个响应全是 fromCache:false。

根因：weApi()（host.js:168-219）只在成功返回后 cache.set， 在途请求没有任何去重。真实触发场景不少：多个浏览器标签页、设置面板开着 + 30 秒轮询、切换跟随显示器。

建议：加一个 pending = new Map()，同 key 的请求复用同一个 Promise；成功后一起写缓存，失败则删掉 pending 让下次重试。

预期：并发 10 → 下游 1 次；WE API 服务的负载下降一个量级。

P1 5. 端点探测串行 5 × 8 秒，挂起时最坏 40 秒

现象：WE 服务端口存在但不响应（挂起 / 被防火墙 drop）时，单次 /we 请求最坏要 40 秒才返回 502。 端口无人监听（ECONNREFUSED）时倒是只要 3 ms，所以这个坑平时不容易遇到。

根因：ENDPOINTS.wallpapers 有 5 个候选路径串行尝试，每个 AbortSignal.timeout(8000) （host.js:117-166）。而且失败结果不写缓存，下一次请求再走一遍全程。

建议：

  • 记住可用端点：首次成功后把 base → 可用 endpoint 存进内存，后续请求直接用它，只在失败时才重新探测。
  • 超时降到 2 s：目标是本机 127.0.0.1 服务，8 s 完全没必要。
  • 加 5–10 秒负缓存：失败也记一笔，避免「面板打开 + 轮询」在服务挂了的时候反复重试。

预期：挂起场景 40 s → 2–10 s；正常场景少 4 次无用请求。

P1 6. /asset 没有 ETag，无法 304

现象：视频二次加载实测 99–104 ms，和首次（104 ms）几乎一样——本地盘 292 MB/s 下重下 5%（28 MB）刚好约 100 ms， 说明没有真正命中条件缓存。

根因：只发了 Cache-Control: public, max-age=300，没有 ETag / Last-Modified（host.js:294-300）。

说明：本地 SATA/NVMe 场景下这 100 ms 并不算痛点，所以这条排 P1 而不是 P0。但换成网络盘、机械硬盘、 或壁纸库在 NAS 上时会被放大；另外 5 分钟缓存过期后，完整看一遍 526 MB 的视频就意味着重新下载。

建议：用已有的 statSync 结果算 ETag = mtimeMs + '-' + size， 请求带 If-None-Match 且匹配时直接回 304。

预期：二次播放/循环队列回到同一张时省掉整段重下。

P2 7. 桌面同步轮询不随页面可见性暂停

现象：开启「同步桌面壁纸」后，即使 DSH 被切到后台，仍每 30 秒发一次请求（每天约 2880 次/标签页）， 并且每次 syncCurrent() 都无条件 emit() 触发一次全量面板重渲染。

根因：window.setInterval 没有可见性判断（client.js:1274-1285）； emit() 在 client.js:993 无条件调用。

建议：visibilitychange 变 hidden 时 clearInterval，变 visible 时立刻 syncNow(true) 并重建定时器 （onVisible 已经有了，只是补上暂停）。emit() 改为仅在壁纸 id 变化或 monitors 变化时调用， 「仅刷新时间戳」用轻量方式单独通知。

预期：后台零请求；前台同步行为不变（切回页签立即跟随本来就是现有特性）。

P2 8. objUrlCache / vidThumbCache 从不释放

现象：上传的图片 / 视频缩略图 objectURL 只增不减，且设置面板卸载时不清。

根因：两个 Map（client.js:1310, 1313）只在删除单张壁纸时 revoke， ctx.effect 的清理函数（client.js:2170-2180）没有碰它们。 每个 URL 都会把对应 blob 钉在内存里——传几个大视频就是几百 MB 常驻。

建议：清理函数里遍历两个 Map 统一 revokeObjectURL（正在当背景显示的那个由 lastObjectUrl 逻辑处理，跳过即可）。

P2 9. 白场片头探测结果只存内存

现象：最坏 613 ms（9 次 seek 串行）。实测样本视频首帧白像素占比 0.03 和 0，都不是白场， 所以实际只做 1 次采样就返回——这一项体感很小。

根因：videoSkipAt 是内存 Map（client.js:264），刷新即失效； 且探测发生在首帧已开始播放之后，会短暂暂停播放。

建议：优先级最低。若要做，把 url → skip 连同缩略图一起落 IndexedDB；或者干脆只在「首帧确实是白场」时才启动完整探测 （现在的 probeStartupWhite 已经是这个逻辑，所以实际已经基本没问题）。

五、本轮处置结果

筛选原则：不碰任何影响画面质量的路径。 「按屏幕分辨率调低内置壁纸请求尺寸」这类能省带宽、但会让高 DPI / 4K 屏发虚的做法被排除； 渲染层（<video> + object-fit、滤镜策略、图层叠化、场景预览图）一律不动。 下面所有改动只涉及缓存、并发、事件订阅与资源释放，画面与画质和改动前逐像素一致。

5.2 因「不影响画质」约束排除

项为什么不做
P0-1a 内置壁纸按屏幕分辨率请求（1920 → 1280） 能省约 40% 流量，但背景图分辨率实际下降 —— 1080p 屏全屏放大后会有可感知的软化，高 DPI / 4K 屏更明显。与约束直接冲突，不做。
P1-5b 把单端点超时从 8 s 压到 2 s 纯参数调整、无画质影响，但会把「基地址指向局域网 / 慢盘时的慢响应」误判成「服务挂了」，属于拿可用性换延迟，本轮保守跳过。

5.3 仍然待定的两项

内置壁纸首屏 1.70 s（P0-1b） —— 唯一一条既能提速、又不降低最终画质的路子是「渐进式出图」： 先用 640 px 小图（几十 KB，约 150 ms）铺上背景，全尺寸 1920 px 图在后台加载完成后静默替换。 最终画质不变，也不引入缓存文件（不违背 README 的 zero-cache 承诺），但过程中会短暂显示一张小图。 要不要做，取决于对「启动头一两秒看到的是不是最终画质」的容忍度 —— 留给你定。

白场片头探测结果落库（P2-9） —— 收益本来就小：实测样本视频首帧都不是白场，实际只做 1 次采样就返回。
